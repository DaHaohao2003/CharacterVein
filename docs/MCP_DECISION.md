# MCP 与 Skill 技术决策

## 结论

比赛版暂不把内部工具改造成 MCP 服务，也不把运行流程包装成 Codex Skill。字脉自身的智能体能力由 LangGraph、类型化 Tool Registry、PostgreSQL/pgvector、MinIO 和模型适配器共同实现；这已经具备自主规划、工具选择、失败回退、证据审校和可审计执行轨迹。

这不是放弃 MCP，而是避免为了展示技术名词引入一层没有实际消费者的协议。当前六个工具都在同一应用进程内，数据权限、事务和任务上下文也都属于字脉 API，直接类型调用更简单、更可靠。

## 当前边界

| 能力 | 当前实现 | 是否需要 MCP |
| --- | --- | --- |
| 文献检索 | `search_literature`，结构化/全文/向量三路召回和 RRF | 否，数据与调用方同属 API |
| 字形检索 | `search_glyphs`，PostgreSQL/pgvector + MinIO | 否，属于内部领域工具 |
| 来源详情 | `get_source_detail` | 否，任务内只读查询 |
| 陈述审校 | `audit_claims` | 否，需要携带任务内声明和证据对象 |
| 内容生成 | `generate_content` | 否，是任务内有状态操作 |
| 约束检查 | `check_constraints` | 否，是确定性本地规则 |

## 何时引入 MCP

满足以下任一条件时，再增加独立的只读 MCP 网关：

1. 需要让字脉以外的客户端（其他智能体、IDE 或研究工具）检索同一份汉字语料；
2. 文献库被拆分为独立服务，并需要稳定的跨进程工具协议；
3. 比赛明确要求展示 MCP 客户端/服务端互操作，而不是仅要求智能体和工具调用；
4. 需要接入外部博物馆、图书馆或知识库提供的 MCP 服务。

首批只暴露 `search_literature`、`search_glyphs` 和 `get_source_detail` 三个只读工具；生成、审校和任务状态修改继续留在应用内部。MCP 服务必须复用现有输入输出模型、鉴权、来源许可字段和工具调用日志，不能形成第二套事实层。

## Skill 的定位

Skill 适合把“如何操作字脉”封装为开发工具或比赛演示助手，但它不应成为产品运行时依赖。产品评审看到的智能体证据应来自字脉页面中的动态计划、工具调用、检索轨迹、审校与回退，而不是依赖 Codex 会话本身。
